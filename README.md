# Learn PySpark 🚀

A hands-on collection of Jupyter notebooks for learning Apache Spark with Python (PySpark), organized as chapters like a textbook. Each chapter builds on the previous one using a common employee dataset, so you can open any notebook and follow along.

## 📖 Table of Contents

| Chapter | Notebook | What You Will Learn |
|---------|----------|---------------------|
| 1 | [Chapter 1 — Spark Introduction & DataFrame Basics](chapter1.ipynb) | Creating a `SparkSession`, building DataFrames from raw data, defining schemas (`StructType` vs DDL strings), checking partitions, `show()` / `printSchema()`, selecting columns with `col()` and `expr()`, casting types with `cast()` and `selectExpr()`, filtering with `where()`, and writing results to CSV. |
| 2 | [Chapter 2 — DataFrame Basics (Practice)](chapter2.ipynb) | A practice run of Chapter 1's concepts: schemas, column selection, expressions, type casting, filtering, and saving output — reinforcing the DataFrame fundamentals. |
| 3 | [Chapter 3 — Column Operations](chapter3.ipynb) | Adding and overwriting columns with `withColumn()`, constant columns with `lit()`, adding multiple columns at once, renaming with `withColumnRenamed()`, dropping columns with `drop()`, filtering rows, and limiting results with `limit()` and `show(n)`. |
| 4 | [Chapter 4 — Data Cleaning & Transformation](chapter4.ipynb) | Conditional logic with `when()` / `otherwise()`, string replacement with `regexp_replace()`, date parsing with `to_date()`, adding `current_date()` / `current_timestamp()`, timezone formatting with `date_format()`, handling nulls with `na.drop()` and `coalesce()`, and reshaping the final DataFrame. |
| 5 | [Chapter 5 — Combining & Aggregating Data](chapter5.ipynb) | Combining DataFrames with `union()` (alias `unionAll()`) and schema-order-safe `unionByName()`, sorting with `orderBy()` (asc/desc), aggregations with `groupBy()` + `agg()` using `sum()` / `avg()` with `alias()`, and SQL `HAVING`-style filtering on aggregated results. |
| 6 | [Chapter 6 — Distinct Data & Window Functions](chapter6.ipynb) | Removing duplicates with `distinct()`, window functions with `Window.partitionBy().orderBy()` — running `max()` over a window, finding the 2nd-highest salary per department with `row_number()`, and writing window expressions as SQL strings with `selectExpr()` and `expr()`. Bonus tip: step-by-step guide to practicing on Databricks Community Cloud (free cluster + notebook setup). |
| 7 | [Chapter 7 — Spark Architecture, Partitioning & Joins](chapter7.ipynb) | Spark architecture notes (driver, master, workers, executors, tasks, and what shuffling is), controlling partitions with `repartition(n)` / `repartition(n, col)` / `coalesce(n)` and inspecting row placement with `spark_partition_id()`, then joining `emp` with a new `dept` DataFrame: inner `join()` with qualified columns and `alias()`, plus multi-condition joins chaining `&` with `isin()` / `isNotNull()`. Links out to the [Spark Architecture note](spark-architecture-notes.ipynb) for the full submit-to-shutdown story. |
| 8 | [Chapter 8 — Reading CSV Files & Corrupt Records](chapter8.ipynb) | Reading real files with `spark.read.format("csv")`: what `header` and `inferSchema` actually cost (extra jobs), forcing a DDL schema with `.schema()` to skip them, then handling malformed data — the `mode` option (`PERMISSIVE` / `DROPMALFORMED` / `FAILFAST`), capturing raw bad lines in `_corrupt_record` and renaming it with `columnNameOfCorruptRecord`, why `FAILFAST` survives `.load()` and only blows up on an action, the `count()`-vs-`collect()` column-pruning trap, Databricks-only `badRecordsPath`, and passing several options at once with `.options(**dict)`. |
| 9 | [Chapter 9 — Reading Parquet & Columnar Storage](chapter9.ipynb) | Row format vs columnar format and why columnar lets a query read only the columns it needs, then reading parquet with `spark.read.format("parquet")` three ways — a whole part-file directory, one self-contained part file, and a `*.parquet` glob — plus nested folders with `.option("recursiveFileLookup", True)`, and a `get_time` Python decorator that times `count()` over all columns against `select("trx_id").count()` to measure column pruning in action. |
| 10 | [Chapter 10 — Reading JSON & Flattening Nested Data](chapter10.ipynb) | Reading JSON with `spark.read.format("json")` — newline-delimited files by default, pretty-printed ones with `.option("multiline", "true")`, and the raw file as a single `value` column via `format("text")` — then forcing a DDL schema for nested types like `array<struct<...>>`, parsing strings with `from_json()` and serialising back with `to_json()`, and flattening the result: `select("parsed.*")` to expand a struct into columns, `explode()` to turn an array into rows, and `drop()` to remove the original array column. |
| 11 | [Chapter 11 — Running on a Real Cluster](chapter11.ipynb) | Moving off `local[*]` onto the Docker standalone cluster: pointing a `SparkSession` at `.master("spark://<master-host>:7077")`, generating rows with `spark.range()`, and writing CSV to the shared `/data` volume — including the `path already exists` failure and fixing it with `.mode("overwrite")`. Then sizing the application with `.config("spark.executor.cores")` / `.config("spark.executor.memory")`, why the standalone manager **ignores** `spark.executor.instances` and `spark.cores.max` is the real dial (executors = total cores ÷ cores per executor), and reading the master UI (`:8080`) and job UI (`:4040`) to match tasks → partitions → part files. Ends with the `spark-submit` equivalent of the same job (`--total-executor-cores`, `--executor-cores`, `--executor-memory`) — 🚧 written up as comments, not yet run. |
| 12 | [Chapter 12 — Python UDFs and What They Cost](chaper12.ipynb) | User Defined Functions: wrapping your own Python with `udf()`, the `@udf` decorator and `spark.udf.register()` for SQL/`expr()`, and declaring return types. Then the price tag — the seven-step journey of a row out of the executor JVM into a separate **python worker** process and back (serialise → row-by-row → serialise), spotting it in a plan as `BatchEvalPython` next to a built-in's plan, the four costs (double serialisation, extra process, one row at a time, Catalyst blindness — no pushdown), and why the python worker sitting *outside* the JVM heap causes `OutOfMemory` on a node (`spark.executor.pyspark.memory` is the only cap, unset by default). Ends with the three fixes, best first: built-ins and **higher-order functions** (`transform` / `filter` / `aggregate` with `x -> x * 2` lambdas that stay in the JVM), a Scala/Java UDF registered with `registerJavaFunction()` so no python worker starts, and vectorised `@pandas_udf` (Arrow, a batch at a time, `ArrowEvalPython`). Opens with a run-environment table, because UDFs are the first chapter where *where* you run matters: the local `.venv` (Python 3.12) cannot pickle a function at all, the Docker Jupyter container on `local[*]` runs everything, and `spark://` cluster runs need `/usr/local/bin/python` symlinked on the Alpine workers (the driver's python path is baked into the shipped UDF) and still cannot do pandas UDFs. |

## ▶️ How to Use

1. Set up a Python environment with PySpark installed (a local `.venv` works fine), or use the Docker cluster in [docker-images/](docker-images/).
2. Start Jupyter and open any chapter notebook.
3. Run the cells top to bottom — every chapter creates its own `SparkSession` and sample data, so chapters are self-contained.
